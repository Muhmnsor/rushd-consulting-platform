# الدليل التنفيذي لمنصة رُشد للاستشارات الشبابية

> هذا الملف هو المرجع التنفيذي للمشروع. عند تعارض تنفيذ تقني مع هذا الدليل أو
> مع قرارات البنية الموجودة في `docs/adr`، يجب إيقاف التنفيذ وتسجيل قرار
> معماري جديد قبل الاستمرار.

## 1. تعريف المنتج

رُشد منصة لإدارة رحلة الاستشارات الشبابية من تقديم الطلب حتى إغلاق الحالة.
تخدم المنصة الفئات التالية:

- المستفيد.
- ولي الأمر أو الممثل المفوض.
- المستشار.
- مشرف الاستشارات.
- منسق الحالات.
- إدارة المركز.
- مدير النظام.
- مراجع الجودة والمدقق وفق نطاق مصرح.

## 2. القرارات المعمارية الأساسية

1. رُشد تطبيق مستقل يملك نماذج بياناته ومنطق أعماله واختباراته وواجهاته.
2. يستخدم Frappe Framework كطبقة تشغيل خلفية، ولا يعدّل Frappe Core.
3. لا يوجد اتصال إلزامي مع شركة Frappe، وتكون الاستضافة Self-hosted داخل
   حساب Azure الخاص بالجهة.
4. لا توجد تحديثات تلقائية للإنتاج. يثبت إصدار Frappe، وتختبر الترقية في
   Staging قبل اعتمادها.
5. قاعدة بيانات رُشد هي مصدر الحقيقة الوحيد للحالات والجلسات والمواعيد
   والموافقات والتقارير.
6. لا يستخدم Supabase في البنية المعتمدة، ولا تُنشأ قاعدة بيانات ثانية
   موازية لقاعدة Frappe.
7. لا تُعرض Frappe Desk للمستفيد أو ولي الأمر أو المستشار.
8. تُفصل الإدارة عن واجهات المستخدمين في النطاق والوصول والجلسات والصلاحيات.
9. إخفاء عناصر الواجهة ليس صلاحية؛ كل عملية تُراجع في الخادم وعلى مستوى السجل.
10. المرفقات الحساسة لا تُنشر بروابط عامة.

القرارات التفصيلية:

- [ADR-0001: حدود اعتماد رُشد على Frappe](adr/0001-platform-boundary.md)
- [ADR-0002: الفصل الكامل بين الواجهات](adr/0002-interface-separation.md)

## 3. الوضع الحالي

الإصدار الحالي للتطبيق: `0.1.0`.

المتوفر حاليًا:

- تطبيق رُشد مستقل عن مستودع Frappe.
- المستفيدون.
- المستشارون.
- الخدمات.
- طلبات الاستشارة.
- الحالات الاستشارية.
- توفر المستشار وإجازاته.
- المواعيد والحجز الأولي.
- ولي الأمر.
- تفويض ولي الأمر محدد المدة والنطاق.
- صلاحيات على مستوى السجل للمستفيد وولي الأمر والمستشار والمنسق.
- مساحة عمل إدارية أولية.
- خط عربي ودعم RTL أولي.
- اختبارات آلية لعزل بيانات الأدوار.

بيئة التطوير الحالية:

```text
Application: consultation_center / رُشد
Framework: Frappe 15.116.0
Development Site: site1.local
Development Database: Local MariaDB
Application Source: rushd-app
```

البيئة المحلية ليست تصميم الإنتاج النهائي. سيعاد إنشاء موقع Staging على
PostgreSQL في Azure قبل التوسع في الميزات.

## 4. بنية Azure المستهدفة

```text
Azure Subscription
└── Resource Group: rushd
    ├── Virtual Network
    │   ├── Application Subnet
    │   ├── Data Subnet
    │   └── Private Endpoints Subnet
    ├── Azure Container Registry
    ├── Azure Container Apps Environment
    │   ├── Rushd Web / API
    │   ├── Frappe Workers
    │   ├── Scheduler
    │   └── Realtime / WebSocket
    ├── Azure Database for PostgreSQL Flexible Server
    ├── Azure Managed Redis
    ├── Azure Storage
    │   ├── Private Files
    │   ├── Public Assets
    │   └── Backup Exports
    ├── Azure Key Vault
    ├── Log Analytics / Application Insights
    └── Front Door / WAF أو بوابة دخول مكافئة
```

يمكن استخدام Azure VM بدل Container Apps إذا أثبت اختبار التشغيل أن ذلك أبسط
وأكثر موثوقية لـFrappe. يجب تسجيل الاختيار النهائي في ADR قبل الإنتاج.

### 4.1 قاعدة البيانات

الخدمة المستهدفة:

```text
Azure Database for PostgreSQL Flexible Server
```

تخزن فيها:

- المستخدمون والأدوار.
- المستفيدون وأولياء الأمور.
- تفويضات أولياء الأمور.
- المستشارون والمشرفون والمنسقون.
- الخدمات والبرامج.
- الطلبات والحالات.
- المواعيد والجلسات.
- الموافقات والمقاييس.
- التقارير وسجلات التدقيق.
- بيانات الإشعارات والتكاملات.

ضوابط القاعدة:

- لا يكون لها Public Access في الإنتاج.
- تتصل بها خدمات رُشد عبر VNet وPrivate Endpoint.
- تحفظ بيانات الاتصال في Key Vault.
- تستخدم TLS أثناء النقل.
- تفعل النسخ الاحتياطية والاستعادة إلى نقطة زمنية.
- ينفذ تصدير منطقي دوري مستقل باستخدام `pg_dump`.
- يختبر Restore فعليًا قبل الإطلاق وبشكل دوري.
- لا تستخدم قاعدة الإنتاج للتطوير أو الاختبارات.

### 4.2 المرفقات والملفات

توضع الملفات في Azure Storage، ولا تعتمد على القرص المؤقت للحاوية.

الملفات الخاصة تشمل:

- صور ومستندات إثبات الهوية.
- مرفقات طلب الاستشارة.
- توقيعات الموافقات.
- تقارير PDF.
- مرفقات الجلسات والحالات.
- أي تسجيل مصرح به مستقبلًا.

الضوابط:

- Private Containers أو Azure Files خاصة.
- لا توجد Anonymous Public Access.
- الوصول عبر Private Endpoint.
- روابط تحميل قصيرة العمر بعد فحص صلاحية المستخدم والسجل.
- تشفير أثناء النقل وفي التخزين.
- تسجيل عمليات الرفع والمشاهدة والتنزيل والحذف.
- سياسة احتفاظ وحذف حسب نوع الملف.
- منع وضع بيانات المستفيد في اسم الملف أو مساره الخارجي.

### 4.3 الأسرار

تحفظ في Azure Key Vault:

- كلمة مرور قاعدة البيانات.
- مفاتيح التشفير.
- مفاتيح Storage.
- مفاتيح SMS والبريد.
- أسرار Webhooks.
- بيانات اعتماد مزودي الاجتماعات.

لا تحفظ الأسرار في:

- Git.
- ملفات Docker Image.
- متغيرات مكتوبة داخل الكود.
- سجلات التطبيق.
- مستندات المشروع.

### 4.4 Redis والمهام

يستخدم Redis في:

- Cache.
- قوائم المهام.
- الجلسات المؤقتة.
- التنسيق بين Workers.

Redis ليس مصدر حقيقة، ولا تحفظ فيه الحالة الرسمية أو التقارير أو الموافقات.

## 5. البيئات

يجب وجود بيئتين مستقلتين على الأقل:

### Staging

- قاعدة بيانات منفصلة.
- Storage منفصل.
- أسرار منفصلة.
- بيانات اصطناعية أو منقحة فقط.
- تستخدم للترقيات وUAT واختبارات التكامل.

### Production

- قاعدة وStorage وأسرار مستقلة.
- وصول إداري مقيد.
- مراقبة وتنبيهات ونسخ احتياطي.
- لا تنشر إليها تغييرات يدوية من أجهزة المطورين.

يمكن إضافة Development مشترك لاحقًا، مع بقاء التطوير المحلي متاحًا.

## 6. فصل النطاقات والواجهات

| النطاق | الفئة | الوظيفة |
| --- | --- | --- |
| `rushd.sa` | عام | الموقع التعريفي والمحتوى العام |
| `portal.rushd.sa` | المستفيد وولي الأمر | الطلبات والموافقات والمواعيد والمقاييس والتقارير المسموحة |
| `staff.rushd.sa` | المستشار والمشرف والمنسق | الحالات والجلسات والإشراف والتنسيق |
| `admin.rushd.sa` | الإدارة ومدير النظام | الإعدادات والمستخدمون والتكاملات والتقارير الإدارية |
| `api.rushd.sa` | الواجهات | API رُشد الموثق |

### 6.1 بوابة المستفيد

تعرض:

- التسجيل والدخول.
- الملف الشخصي.
- تقديم طلب استشارة.
- حالة الطلب.
- الموافقات.
- المواعيد والإلغاء وإعادة الجدولة.
- المقاييس المكلف بها.
- تقارير المستفيد المعتمدة فقط.
- الإشعارات.

لا تعرض:

- الملاحظات الداخلية.
- ملاحظات المستشار الخاصة.
- مراجعات المشرف.
- بيانات مستفيد آخر.
- إعدادات الإدارة.

### 6.2 بوابة ولي الأمر

لا يحصل ولي الأمر على وصول لمجرد وجود صلة قرابة. يشترط تفويض:

- فعال.
- محدد للمستفيد.
- محدد المدة.
- محدد النطاق.
- غير مسحوب أو منتهي.

نطاقات التفويض الممكنة:

- مشاهدة الملف.
- مشاهدة الطلبات.
- مشاهدة الحالة.
- إدارة المواعيد.
- مشاهدة التقارير المصرح بها.

### 6.3 واجهة المستشار

تعرض:

- الحالات المسندة إليه فقط.
- جدول مواعيده.
- توفره وإجازاته.
- تسجيل الجلسات.
- الملاحظات الاستشارية الخاصة.
- المقاييس المرتبطة بالحالة.
- التقارير وخطط المتابعة.
- طلب إشراف أو إحالة.

لا تعرض:

- حالات مستشار آخر.
- إعدادات النظام.
- بيانات إدارية لا يحتاجها.
- سجلات حساسة خارج حالات التكليف.

### 6.4 واجهة المشرف

تعرض:

- الحالات ضمن نطاق إشرافه.
- الحالات المنتظرة للإسناد.
- توزيع وإعادة إسناد الحالات.
- طلبات المراجعة.
- اعتماد التقارير أو طلب تعديلها.
- مؤشرات الجودة والأداء المصرح بها.
- التنبيهات ومخاطر التأخير.

### 6.5 واجهة المنسق

تعرض:

- الطلبات الجديدة.
- استكمال البيانات.
- حالة الموافقات.
- جدولة المواعيد.
- الحضور والتذكيرات.
- مهام التنسيق.

لا تعرض الملاحظات الاستشارية السرية إلا بقرار صلاحية موثق.

### 6.6 واجهة الإدارة

تكون على نطاق مستقل، وتشمل:

- المستخدمين والأدوار.
- الخدمات والبرامج.
- إعدادات النظام.
- قوالب الإشعارات.
- التكاملات.
- مؤشرات الإدارة المجمعة.
- سجلات التدقيق.
- سياسات الاحتفاظ والنسخ.

ضوابطها:

- MFA إلزامي.
- قيود شبكة أو وصول خاص.
- Session منفصلة عن بوابات المستخدمين.
- أقل صلاحية.
- تسجيل العمليات الإدارية الحساسة.

## 7. API رُشد

لا تستدعي واجهات المستخدم REST API العامة التي ينشئها Frappe مباشرة. يبنى API
محدد لرُشد:

```text
/api/rushd/auth
/api/rushd/profile
/api/rushd/guardians
/api/rushd/services
/api/rushd/requests
/api/rushd/cases
/api/rushd/appointments
/api/rushd/sessions
/api/rushd/assessments
/api/rushd/reports
/api/rushd/notifications
```

ضوابط API:

- فحص الهوية والدور في كل طلب.
- فحص ملكية أو إسناد السجل.
- منع Mass Assignment.
- Response Schemas محددة.
- عدم إرجاع الحقول الداخلية افتراضيًا.
- Rate Limiting.
- CSRF/CORS مضبوط للنطاقات المعتمدة.
- Idempotency للعمليات الحساسة والتكاملات.
- عدم تسجيل Payload حساس كاملًا.
- اختبارات IDOR لكل Endpoint.

## 8. نموذج العمل للنسخة الأولى

### 8.1 المستفيد وولي الأمر

- إنشاء المستخدم.
- إنشاء ملف المستفيد.
- ربط ولي الأمر عند الحاجة.
- إصدار تفويض ولي الأمر.
- تسجيل الموافقة وقالبها وإصدارها.

### 8.2 الخدمة والطلب

- تعريف الخدمة وشروط الأهلية.
- تقديم الطلب.
- مراجعة الاكتمال.
- طلب معلومات إضافية.
- تحديد الأهلية.
- انتظار الموافقة.
- تجهيز الطلب للإسناد.
- تحويل الطلب إلى حالة.

### 8.3 الحالة والإسناد

- إنشاء الحالة.
- تحديد المسؤول والمنسق والمشرف.
- إسناد المستشار.
- تحديد الأولوية والسرية.
- تحديد عدد الجلسات والهدف.
- متابعة الإجراء التالي وموعده.

### 8.4 الحجز

- جدول توفر أسبوعي.
- الإجازات والحجب الاستثنائي.
- مدة الخدمة.
- Buffer قبل الموعد وبعده.
- منع التعارض.
- الحد اليومي.
- الحجز والإلغاء وإعادة الجدولة.
- التحقق داخل Transaction لمنع السباق.
- المنطقة الزمنية `Asia/Riyadh` افتراضيًا.

### 8.5 الجلسة

- إنشاء جلسة من الموعد.
- تسجيل الحضور والمدة.
- ملخص مسموح للمستفيد.
- ملاحظات خاصة للمستشار.
- النتائج والتوصيات.
- الخطوة التالية.
- مؤشرات المخاطر والتصعيد.
- منع تعديل السجل المعتمد بلا Amendment أو Revision.

### 8.6 الإشراف والتقرير

- رفع التقرير للمراجعة.
- طلب تعديلات دون تغيير نص المستشار مباشرة.
- إعادة الإرسال.
- الاعتماد.
- نسخة داخلية منفصلة عن نسخة المستفيد.
- عدم مشاركة التقرير قبل الاعتماد عند اشتراطه.
- Revision لأي تعديل بعد الاعتماد.

## 9. ما يدخل في MVP

### Must

- المستفيدون وأولياء الأمور.
- التفويضات والموافقات.
- المستشارون والخدمات.
- الطلبات والحالات.
- الصلاحيات على مستوى السجل.
- الحجز والمواعيد.
- الجلسات والملاحظات.
- إشراف أساسي.
- مقياس قبلي/بعدي بسيط.
- تقرير ختامي مع مراجعة.
- بوابة المستفيد وولي الأمر.
- واجهة المستشار والمشرف والمنسق.
- لوحة إدارة أساسية.
- Email أو SMS عبر مزود واحد.
- Audit وBackup وRestore.

### يؤجل

- WhatsApp.
- الدفع.
- تطبيق جوال Native.
- مساعد ذكاء اصطناعي.
- تحليل النصوص.
- منشئ تقارير ديناميكي متقدم.
- عدة مزودي اجتماعات في النسخة الأولى.
- Data Warehouse.
- Multi-tenancy معقد.
- تسجيل الجلسات افتراضيًا.
- أي تشخيص أو قرار آلي.

## 10. التكاملات

لا يضاف تكامل قبل وجود حاجة مثبتة وقرار يحدد البيانات التي ستغادر النظام.

ترتيب التنفيذ:

1. البريد.
2. مزود SMS واحد.
3. رابط اجتماع يدوي أو مزود واحد.
4. Calendar عند الحاجة.
5. تكاملات أخرى بعد استقرار MVP.

كل تكامل يحتاج:

- Adapter مستقل.
- أسرار في Key Vault.
- Webhook Signature Verification.
- منع Replay.
- Idempotency.
- Retry مضبوط.
- Redacted Logs.
- سجل حالة التكامل دون Payload حساس.

## 11. الأمن والخصوصية

متطلبات إلزامية:

- أقل صلاحية.
- MFA للموظفين المميزين.
- TLS.
- تشفير الأسرار والملفات الحساسة.
- Field Permission Levels.
- Permission Query Conditions.
- Document-level Permission Checks.
- منع IDOR.
- منع Privilege Escalation.
- حماية XSS وCSRF.
- فحص المرفقات ونوعها وحجمها.
- منع الروابط العامة.
- Rate Limiting وCaptcha عند الحاجة.
- Secret Scanning وDependency Scanning.
- SAST وDAST.
- تنقيح بيانات Staging.
- سياسة احتفاظ وحذف.
- سجل وصول وتغيير.
- إبطال وصول الموظف فور انتهاء العلاقة.
- اختبار اختراق قبل الإنتاج.

متطلبات رحلة القاصر:

- تحديد متى يلزم ولي الأمر.
- توثيق الأساس النظامي والموافقة.
- تحديد ما يستطيع ولي الأمر رؤيته بدقة.
- آلية سحب أو انتهاء التفويض.
- بروتوكول للتصعيد والمخاطر والطوارئ.
- مراجعة قانونية وتنظيمية داخل السعودية قبل الإطلاق.

## 12. النسخ الاحتياطي والتعافي

يجب تغطية:

- PostgreSQL.
- المرفقات.
- مفاتيح التشفير المطلوبة للاستعادة.
- إعدادات التطبيق.
- إصدارات Docker Images.

الحد الأدنى:

- نسخ آلية يومية.
- Point-in-time Recovery للقاعدة.
- نسخة منطقية مستقلة.
- احتفاظ طويل حسب السياسة.
- نسخة في نطاق فشل مستقل عند الحاجة.
- اختبار استعادة موثق.
- RPO وRTO معتمدان قبل الإنتاج.
- Runbook للاستعادة والتراجع عن الإصدار.

## 13. المراقبة والتشغيل

المؤشرات:

- توفر الواجهة وAPI.
- زمن الاستجابة.
- أخطاء 4xx و5xx.
- فشل Workers والمهام.
- طول Queues.
- اتصالات واستهلاك PostgreSQL.
- استهلاك Storage.
- فشل الإشعارات والتكاملات.
- محاولات الدخول الفاشلة.
- أحداث الصلاحيات غير الطبيعية.
- نجاح النسخ الاحتياطية.

التنبيهات لا تحتوي بيانات مستفيد أو نصوص جلسات.

## 14. CI/CD وإدارة الإصدارات

كل تغيير يمر عبر:

1. Branch أو Pull Request.
2. مراجعة كود.
3. فحوص تنسيق وتحليل ثابت.
4. اختبارات Unit وIntegration.

- كل عملية حساسة مسجلة.
- الملفات الحساسة غير عامة.
- RTL والطباعة العربية صحيحان.
- النسخ الاحتياطي ناجح.
- اختبار الاستعادة ناجح.
